# S2636 object boundary

Expectations recorded before implementation, 2026-10-11. Manufacturer reference:
Valvo/Signetics 2636I preliminary specification, 15-page scan, especially PDF
pages 3-7 and 11 (printed pages 2-6 and 10). Source:
https://www.valoroso.it/file-share/documenti-manuali/Signetics-2636-PVI.pdf,
SHA-256 `5d5d24ace87a723b5f4a3d6ccb72a0451dafa75b07619a7903d4492ea12988da`.
Relevant complete pages were visually inspected; OCR is unavailable. Private
scan and renders remain ignored. MAME s2636.cpp at the existing pinned revision
has SHA-256 `aef1f712c36809c2c35393fedeb9501f419d9c6ac2a973b1151b83ce5515d54d`.
It provides a compatibility cross-check, not a board measurement. Its comments
explicitly acknowledge incomplete access semantics and display-offset limitations.

This module implements four object engines and their status. It is not a full
PVI: background grid, score, sound, ADC, chip enables, physical OPREQ/OPACK and
analog/open-drain outputs remain unimplemented. Stored controls for those future
features do not establish feature coverage. CVS board counter phases, visible
crop and the physical PCK clock must still be audited. The CVS composition
boundary applies MAME's S2636 horizontal device offset of -26 to HC/HCB; the
normalized object engine accepts that fixed offset as a parameter for both
rendering and collision geometry.

## Registers and interface

Only the low byte of internal Fxx addresses is exposed. Object descriptors begin
at 00,10,20,40. Each has ten pattern bytes, then HC,HCB,VC,VCB. Scratch storage
is 0E..0F,1E..1F,4E..6D,AD. Background storage 80..AC and controls C0..C3,C6..C9
are retained for compatibility/future use. C0..CF aliases at D0,E0,F0 decode to
the same controls. C0 holds object scales in two-bit fields, object 1 lowest.
C1 holds object 1 colour in bits 5:3 and object 2 in 2:0; C2 similarly holds
objects 3/4. The three colour bits are ORed for simultaneously drawn objects.
Presence remains true for a drawn black object (colour zero).

CA is read-only completion status: objects 1..4 are bits 3..0. Its high
object/background collision bits are not implemented. CB is read-only VRLE
(bit 6) plus object pairs 1/2,1/3,1/4,2/3,2/4,3/4 in bits 5..0. Reading either
clears that register only. VRST leading edge sets VRLE and pending IRQ; trailing
edge clears status/IRQ and latches primary VC. Completion raises IRQ on the last
object line; acknowledgement clears IRQ. Status reads do not acknowledge IRQ.
New events win simultaneous acknowledgement/read-clear (FPGA collision contract,
not measured physical ordering). Writes to CA/CB are ignored. Holes and pending
ADC registers read FF and ignore writes. Reads of stored write-only controls
return the stored byte for MAME compatibility; their physical read bus is unknown.

CPU data is combinational so the existing banked memory can capture it at its
accepted read edge before status clears. Strobes must already be qualified by
chip selection. Reset clears engine/status/output state but never register RAM.
Tests initialize every descriptor and used control before scanning.

## Normalized rendering contract

VRST is a synchronous level. After its falling edge, a separate line_start edge
prepares each active line, followed by ce_pixel edges at x=0..243. Coordinates
count skipped clocks/lines from this normalized origin; they are not a measured
CVS screen origin. Patterns are MSB first. Scale s produces width 8*2^s and height
10*2^s. Primary VC is latched per field. Scale is latched per field in this first
boundary; mid-object scale changes remain a coverage gap. Primary HC and pattern/
colour bytes are live; partially drawn lines during writes need later physical
timing validation. Duplicate HC is sampled per line, as the manufacturer states.

A primary starts after VC skipped lines. On its last line VCB is sampled and
VCB+1 lines are skipped before the duplicate. Further duplicates use HCB and the
same shape/scale. VCB=FF means 256 skipped lines, never zero via eight-bit wrap.
For the datasheet example VC=36, height=10, VCB=9, starts are 36,56,76,... .
Descriptors with HC outside the sampled horizontal span produce no pixels.
Rendering is sampled one master edge after ce_pixel, and holds with ce_pixel low.
Completion is marked at line_start of the last rendered line, even for a zero
pattern. Actual sub-line completion/OPACK timing remains unqualified. Current-line
geometry persists if the next duplicate is scheduled on that edge.

## Frame clearing and bullet lifetime

The CVS PVI has no persistent sprite bitmap in this RTL. Object pixels are
recomputed from the register image and current raster counters; the first visible
line after VRST reloads VC and resets `in_object`, duplicate mode, and active-line
state. A two-field regression moves an object from x=12 to x=90 and checks every
pixel in both fields, including that the previous position is empty. The core
does not need a vblank sprite-memory wipe. Pinned MAME similarly clears each
S2636 bitmap scanline before drawing it, then reloads VC and resets duplicate
tracking at the first visible line after VRST; the CVS screen update calls all
three PVI renderers each frame.

Bullet RAM is different: it stores one horizontal position per scanline and is
not automatically cleared each frame. MAME's CVS screen update draws each
nonzero entry at rows 8..255; software must write zero to remove a bullet. The
RTL likewise reads the current row's bullet byte while producing each pixel and
does not wipe that RAM on VRST. A retained nonzero byte can therefore persist by
design; it is not a stale rendered bullet plane.

The CVS boundary uses fixed offsets from MAME's `set_offsets(-5, -26)` call.
The S2636 API order is `(y_offset, x_offset)`. The composed PVI field begins
eight lines before the visible crop, so the configured Y translation is +3
relative to that field origin; X remains -26 game pixels. These fixed values
feed the shared object hit mask used by rendering and collision calculations.
They are MAME compatibility values, not independently measured board offsets.

The earlier qualitative core/MAME screenshot comparison was not a matched-frame
test. Its saved images have different frame numbers and no matched game-RAM
checkpoint. `build/ghost-audit-20261016T1824/pixel-diff.json` records exact
pixel metrics and source-image hashes, but explicitly marks them descriptive
only. A defensible game-frame comparison still needs both captures aligned to
the same game state; do not treat visual similarity between unrelated animation
instants as evidence that sprite trails are expected.

Independent tests will use geometric expansion of pattern bits and a list of
analytic duplicate start rows, rather than the HDL's countdown state. They will
compare every pixel and presence/colour/object mask across all four scales,
isolated and overlapping objects, all six pairs, zero-colour and zero-pattern
cases. Directed tests cover status aliases/read-clear/readonly, VRLE/IRQ/reset,
VC field latching, HCB line latching and VCB last-line sampling. Output artifacts
are synthetic pixel diagnostics only, never game captures or ROM/register dumps.
Important faults must fail designated assertions twice in disposable snapshots.

Missing coverage remains explicit for the full PVI, physical origins/timing,
display arbitration, CPU/three-chip integration until tested, mixed game video,
inter-chip/background/bullet collisions, game boot and Quartus implementation.

## Horizontal alias and duplicate audit

The object renderer compares the complete 8-bit `pixel_x` and 8-bit HC value
after adding signed `X_OFFSET`. It forms a signed distance, clips
negative starts at screen X=0, and checks the distance against the scaled
eight-pixel object width. The vertical line wait is
9 bits so the encoded VCB value 255 can represent the 256-line duplicate
interval; the current object-row index is 7 bits and covers the maximum scaled
height. No low-five-bit coordinate truncation was present.

Duplicate scheduling is vertical: object completion loads the VCB wait and
samples HCB for the next duplicate X position. HCB is latched at the line
boundary; a duplicate is started after the configured number of rows. This
matches the duplicate-counter structure in the pinned MAME S2636 implementation
(`src/devices/machine/s2636.cpp`), but does not establish physical PVI timing or
CVS board phase equivalence. The CVS object layer is generated from current
descriptor and raster state; it is not a stored frame plane that requires a
per-frame erase.

The focused single-descriptor test now runs first and scans all 244 horizontal
positions for every one of 256 lines. A solid object at X=35 must produce only
the eight pixels X=35..42 on each of its ten rows, for exactly 80 object pixels
in total. The baseline passes. A disposable RTL mutation that truncates the
horizontal distance operands to five bits fails the designated
`single_object_horizontal_run` assertion reproducibly twice. This disproves
the proposed low-five-bit alias in the current RTL and demonstrates that the
new check detects it. It does not explain the photographed repeated figures.

No new MAME game-frame comparison was made. The retained preview pair has
different frame numbers and no matched game-RAM checkpoint, so its pixel diff
remains descriptive only. A valid game comparison still requires the same ROM,
reset point, input sequence, and matched frame/state checkpoint on both sides.

## Three-chip connection expectations, before implementation

The existing bus selects bit 2 at 1500, bit 1 at 1600 and bit 0 at 1700,
only with FLAG low. The bank will preserve that ordering and combinational read
data, qualify each chip's read/write separately, and return FF with no selection.
Only one chip may be selected by the real decoded bus. Pixels are three packed
{presence,colour} nibbles, chip 1 lowest. There is no inter-chip mixer/collision
logic in this boundary and chip IRQ routing to physical CVS remains unaudited.

The actual-CPU test will initialize all three instances through downloaded
synthetic instructions, then independently check distinct descriptor bytes
81/42/24, FLAG-high character writes preserving those bytes, per-chip VRLE
read-clear, sampled object pixels and completion read-clear. After a normalized
20-line scan, a test-fixture interrupt resumes HALT through vector 03 so CPU
instructions can read completion flags. This fixture IRQ is not a claimed board
interrupt path. All fifteen-plus expected signatures must originate in actual
CPU memory reads/writes; no mock CPU or direct hierarchical register writes.

## Diagnostics and first executed observations

The single-chip geometric baseline passed and its 244x256 synthetic image is
byte-identical to the independent reference. The first alias test incorrectly
expected the initial byte after subsequent alias writes; it now tracks the
explicit stimulus's preceding write. No HDL or observed output was substituted
for the expectation. The first connected compilation rejected unsupported
Icarus `break` statements; bounded loop conditions replace them. These attempts
remain FAIL/ERROR evidence, not successful mutation catches.

The connected CPU simulation then satisfied all eighteen signatures and sampled
pixels. Icarus -Wall reports full-array sensitivity for the indexed combinational
reads. Review: registers has 256 words; active_duplicate, duplicate_hc, render_row,
scale, active_line, in_object and next_row each have four words. Including every
entry is required for these combinational readers and Verilator -Wall is clean.
The adapter retains each exact notice and its reason in the result; its narrowly
matched source/array/size/message list accepts no other diagnostic. There is no
global warning suppression. Native CPU unknown-value diagnostics remain open.

Synthetic image files are P3 pixel diagnostics stored as .log so the pinned
runner retains them. They contain rendered test pixels only, not register RAM or
ROM bytes. Display RGB is a diagnostic mapping of the three colour bits, not
the CVS PROM/palette circuit. The generic framework is unchanged.

The strengthened baseline also checks simultaneous new completion/read-clear,
new completion/IRQ acknowledgement and new collision/read-clear. An overlapping
shared-colour scene distinguishes wire-OR from XOR, and an odd-to-even duplicate
HC change tests a single live-bit fault after line sampling. These assertions
passed. The three-chip CPU baseline passed after the sensitivity review; exact
notices remain attached to its PASS, rather than silently disappearing.

Sixteen new deliberate faults exercise pattern direction, horizontal/vertical
scale, colour OR, status clearing, VRLE bit, duplicate gap/HC cadence, VC field
latching, completion numbering, black presence, simultaneous events, collision
numbering, aliases, chip readback and cross-chip read-clear. The campaign totals
50 faults, each requiring a passing baseline and two identical designated
assertion failures. No unqualified RBF or full PVI accuracy is claimed.

To render a retained pair, use `tools/render_sprite_diag.py observed.log
--expected expected.log --output results/<run>/sprite-preview.png`. It checks
every RGB byte before nearest-neighbour scaling and records input/output hashes,
Pillow version and synthetic provenance. Generated images and metadata stay ignored.
